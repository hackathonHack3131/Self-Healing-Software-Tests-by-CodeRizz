Architecture & Global System Rules

A deep dive into how SelfHeal reconstructs multi-step workflows from immutable business intent without compromising safety, truthfulness, or verifier determinism.

1. The Problem With "Locator Renaming"

Most commercial "AI test healing" tools implement a simplistic heuristic: if #checkout-button fails, search the DOM for a button with text "Checkout" and update the locator.

This fails completely in real-world software engineering. When a product undergoes a redesign, single-page forms are routinely split into multi-step wizards across separate routes (/cart → /shipping → /payment → /review). A locator replacement cannot solve this because the missing fields do not exist on the current page.

SelfHeal redefines healing as complete workflow reconstruction: The test is an immutable business goal with parameterised data and deterministic invariants. When UI drift is detected, an autonomous Deep Agent inspects the new interface, navigates through the multi-step stages, validates each action against security constraints, and builds a new candidate recipe from what actually executed.

2. The Global Integrity Rules

Deterministic Safeguards
Rule Standard Enforcement Mechanism
Rule 1 Immutable Intent The intent file, test data, and expected invariants are never modified. The cryptographic SHA-256 intent hash is verified every time a recipe is loaded.
Rule 2 No Literal Data in Steps Recipe steps never store hardcoded strings, passwords, or cards. Fill steps reference field_key identifiers only.
Rule 3 Code Validates, Not LLMs The model proposes steps; deterministic code validates and executes them. Zero LLM-generated Python, JavaScript, shell, eval, or exec.
Rule 4 Controlled Semantic Actions Only goto_start, fill_field, and click_button are permitted. Targets resolve to exactly one visible, enabled element matched by exact accessible name.
Rule 5 Deterministic Verifier Success is decided exclusively by deterministic code on a clean replay in a fresh browser context. The agent has no tool that declares success.
Rule 6 Status Computed by Code Status codes (PASS_NO_HEAL, PASS_AFTER_HEAL, FAIL_FUNCTIONAL) are computed by rules, never by the model. Model text is labeled as explanation.
Rule 9 Origin Allowlist Guard Chromium visits only registered origins (http://127.0.0.1:5000). All outbound requests outside the allowlist are aborted by client route guards.
Rule 12 Never Fake AI Missing config returns BLOCKED_CONFIG. Model rate limits (429) return BLOCKED_AGENT. Fallbacks to verified traces are strictly labeled RECORDED and must pass clean replay.

3. Technical Components & Stack

Playwright Async Browser Engine

Asynchronous headless Chromium execution via async_playwright. Built-in network routing guards, console error listeners, and live response monitoring.

Accessible DOM (AOM) Snapshot

Extracts accessible roles, names, and controls directly from the browser tree. Strips sensitive customer data, passwords, and payment inputs before analysis.

Levenshtein Structural Diffing

Compares live UI inventories against Version A baseline snapshots. Detects added, removed, and renamed controls with similarity confidence scores.

Rule-Based Triage Engine

Deterministic triage separates application bugs (HTTP 500, visible alert errors, invariant calculation mismatches) from harmless UI drift before any LLM is called.

Deep Agent Observe-Act Healer

LangChain / Deep Agents controller running streaming observe-act loops with subagent failure analysis, recursion limits, and proposal validation.

Local MongoDB Persistence

Connected to local MongoDB instance (localhost:27017). Collections for test execution runs, versioned recipes, and contact submissions with fallback support.
